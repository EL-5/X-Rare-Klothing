## Variants, images, inventory

- **Variants**: every product has 2–6 color variants; sized categories (clothing, belts, socks)
  additionally vary sizes 3–6 deep from the category's real size range (letter sizing for tops/
  outerwear, waist sizing for denim/trousers/belts, S/M–L/XL for socks). Counts are intentionally
  uneven product-to-product, not a fixed grid, per the brief's own "avoid mathematically
  repetitive" instruction.
- **Images**: 2–5 per product, drawn from a per-category pool of 9–28 verified, real, licensed
  Unsplash photographs (photographer credit convention matches
  `docs/image-sources.md`; the running attribution table was not re-duplicated here to avoid
  drift between the two docs — see that file for the format). Images are attached at the product
  level, not pinned to a specific color variant: the pool is real category-appropriate stock
  photography standing in for commissioned product photography, and pinning a specific photo to
  a specific colorway would mean asserting a match ("this photo is the Burgundy one") that isn't
  actually true of a stock photo — the same "don't invent data" discipline used throughout this
  project's imagery work (see `docs/xrare-brand-guidelines.md`'s photography section).
- **Inventory**: every variant's stock was written through `inventory_movements` (a `restock`
  entry, so the ledger — not a direct table write — is what derives `inventory.on_hand`,
  matching the existing architecture in `docs/database.md`). Stock is assigned per product, not
  per variant, using the brief's own tiers: ~5% of products out of stock (a `restock` followed by
  a `sale` movement that fully depletes it, rather than fabricating an on_hand of zero that
  bypasses the ledger's own arithmetic), ~15% low stock (1–15 units), ~10% popular (50–150
  units), and the remaining ~70% normal (10–60 units).

## Pricing

Prices vary by category (a tee and an overcoat don't share a range) and, within
Accessories / Lifestyle specifically, by sub-type — belts, sunglasses, watches, jewelry, and
scarves each have their own realistic range rather than one flat range spanning $18–240, which
was an actual bug caught during live verification (see below) and fixed in migration `0049`.
~15% of products carry a `compare_at_price_cents` 15–40% above their price.

## Known, deliberate scope limits

- **Only one real brand** (X-Rare) exists, so every generated product belongs to it — inventing a
  second brand to demonstrate multi-brand merchandising would violate the same "don't invent
  data" rule this whole session has followed. The brand/category/variant plumbing itself is
  brand-agnostic and already proven end-to-end (see `docs/xrare-multibrand-architecture.md`).
- **No color-specific product images** — see "Variants, images, inventory" above.
- **Descriptions are template-composed, not individually hand-written** — each is assembled from
  independently-varied opener/fit-or-detail/material/use/care phrase banks (see the generator),
  giving thousands of possible combinations per department rather than one fixed sentence
  structure repeated 301 times. They are English prose, not placeholder text, and every one
  falls inside the 50–120 word target.

## Bugs found and fixed during live verification

Generating a catalog at this scale surfaced three real, previously-latent bugs in code that
predates this batch — none of these were problems with the generated data itself, but with
application code that had never been exercised at more than a handful of products:

1. **`useProductListing`'s raw fetch was hardcoded to `pageSize: 200`.** An unscoped `/shop` view
   fetches the full active catalog once for client-side filtering (see the hook's own comment);
   at 200 it would have silently dropped the tail of the catalog. Raised to 1,000 with a comment
   explaining the real fix (server-side faceting) once the catalog outgrows even that.
2. **`.in('variant_id', …)` calls with thousands of ids blew past a practical URL length limit
   and returned HTTP 400** — hit by `inventoryRepository.getByVariantIds` (used by every
   unscoped shop/category view to compute in-stock filtering) and `listAllWithVariantInfo` (the
   admin Inventory page). Fixed by chunking both into batches of 300 ids run in parallel via a
   shared `chunkedIn` helper.
3. **`variants_by_products` and a plain `product_images` select silently truncate at Supabase's
   platform `db-max-rows` cap (1,000 on this project)** — for an unscoped listing across hundreds
   of products this returned a `200 OK` with a partial result rather than an error, so the
   products whose rows fell after row 1,000 rendered with **no variants at all** (`$0.00`,
   "Sold Out") despite having correct data in the database. This is worse than an outright error
   because nothing in the UI signaled a problem. Fixed by chunking product ids into groups of 20
   per request in `productRepository`'s `fetchVariants`/`fetchImages`.

All three are now covered by a shared "chunk large id lists" pattern rather than three different
ad hoc fixes, and are general fixes — they help any future growth of the catalog, not just this
batch.
